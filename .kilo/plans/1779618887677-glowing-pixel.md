# Plan: Resolve OpenCL Dependency in nano-rspow-node

## The Problem
Yes, your assessment is correct! Because the `opencl` feature is currently enabled for `nano-rspow-node` in its `Cargo.toml`, the resulting `.node` native addon links directly to OpenCL (`libOpenCL.so.1` on Linux). 

As a result, **any user who installs `nano-rspow-node` must have OpenCL runtime libraries installed on their system just to `require()` the module.** If they don't, Node.js will throw a dynamic linker error (`cannot open shared object file`), completely breaking the package—even if the user only wanted to use the CPU or WGPU backends.

## Proposed Solutions

### Option 1: Remove OpenCL from the Node Package (Recommended)
Since `nano-rspow-node` already enables the `wgpu-backend` feature, it has excellent, modern GPU support out-of-the-box (Metal on Mac, Vulkan on Linux, DX12 on Windows). OpenCL is mostly redundant for these users.
*   **Action:** Remove the `"opencl"` feature from `nano-rspow-node/Cargo.toml`. 
*   **Result:** The strict load-time dependency is eliminated. Users can `npm install` without needing OpenCL. The core Rust crate (`nano-rspow`) and CLI will still have OpenCL available as an opt-in feature.

### Option 2: Switch to Runtime Dynamic Loading (Complex)
If OpenCL is strictly required for the Node package, we would need to stop linking it at compile time. 
*   **Action:** Refactor the OpenCL backend in `nano-rspow` to use a crate that supports dynamic library loading at runtime (like `opencl3` with dynamic features, or raw `libloading`). 
*   **Result:** The module will load successfully and OpenCL will simply gracefully fail or be marked as "unavailable" if `libOpenCL.so.1` is missing. 

### Option 3: Separate Packages
*   **Action:** Publish `nano-rspow-node` (without OpenCL) and a separate `nano-rspow-node-opencl` package for legacy hardware.
